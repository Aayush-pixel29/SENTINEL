# SENTINEL-X Threat Model & Security Specification

## 1. Scope & Objective

This document defines the threat model, trust boundaries, adversarial attack vectors, and defensive mitigations for **SENTINEL-X**.

SENTINEL-X serves as a deterministic control plane operating between semi-autonomous / autonomous AI agents and execution runtimes (operating system, tools, APIs, repositories).

## 3. Threat Vectors & Mitigations

### 3.1 Unallowlisted & Blocked Tool Execution
* **Threat**: An agent hallucinates or is coerced into requesting dangerous tools (e.g. `raw_bash_exec`, arbitrary curl/wget, internal socket access).
* **Mitigation**: `ToolShield` evaluates tool requests against an explicit registry. If a tool is not explicitly registered and enabled with trusted status, execution is immediately **DENIED** (`RULE_001_ALLOWLIST` / `RULE_003_BLOCKED_TRUST`).

### 3.2 Tool Selection Manipulation
* **Threat**: Adversarial prompts in repository files or tool docstrings convince an LLM to select an insecure tool.
* **Mitigation**: Tool trust is never derived from model perception or LLM reasoning. Tool permissions, risk levels, and operations are hardcoded in static policy.

### 3.3 Unsafe Tool Arguments (Path Traversal & Command Injection)
* **Threat**: An authorized tool (e.g. `read_repository`) is given hostile arguments such as `../../../../etc/passwd` or command chaining `; rm -rf /`.
* **Mitigation**: `ArgumentValidator` scans all arguments for directory traversal sequences, command separators, shell pipes, subshell invocations, and destructive commands prior to dispatch.

### 3.4 Credential & Secret Leakage in Tool Outputs
* **Threat**: An authorized tool fetches configuration files or database connection strings containing plaintext passwords or API keys that leak into agent context and logs.
* **Mitigation**: `OutputSanitizer` intercepts all tool return values, redacting database connection credentials, API keys (OpenAI, Gemini, GitHub, AWS), Bearer tokens, private keys, and PII before passing data back to agent memory or telemetry.

### 3.5 Double-Spend / Duplicate Execution of Side-Effects
* **Threat**: Network retries or agent loops cause state-mutating actions to execute multiple times.
* **Mitigation**: `ExecutionManager` enforces idempotency keys, caching completed execution records and returning stored results without re-invoking underlying handlers.

### 3.6 Unverified AI Model Assertions (Hallucinated Safety)
* **Threat**: An LLM reviewer falsely asserts that vulnerable code is safe or hallucinates false positives.
* **Mitigation**: Strict classification separation:
  - **CONFIRMED**: Backed by deterministic tool exit codes and AST findings (Semgrep, Pytest, Gitleaks).
  - **UNCONFIRMED**: Generated by AI models (Gemini critic), triggering `REVIEW` status rather than automatic approval.

## 4. Residual Limitations

1. **Local-First Boundary**: ToolShield enforces local policies. It does not replace network firewalls or sandboxed containers for untrusted multi-tenant execution.
2. **Regex-Based Sanitization**: Sanitization relies on pattern matching for known token/credential formats and sensitive schemas. High-entropy bespoke secrets should also be guarded via environment separation.
3. **Deterministic Scope**: Deterministic checks are only as comprehensive as the configured tools (e.g., Pytest coverage, Semgrep rulesets).
